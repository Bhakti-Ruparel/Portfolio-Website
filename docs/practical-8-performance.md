# Practical 8: Performance Optimization and Lazy Loading in React

## Objective

This practical focuses on improving frontend performance by reducing the initial JavaScript loaded on first paint using React lazy loading, route-based code splitting, and smart loading states. The goal is to keep the app responsive while preserving existing functionality and user routes.

## Existing Application

This project is a full-stack portfolio and task management app built with React and Vite on the frontend, with a Node.js backend for authentication and task APIs. It includes a portfolio landing page, project section, contact section, GitHub repos viewer, to-do management, and protected task routes. The app uses React Router for navigation and retains the existing authentication flow and API integration.

## Implementation

### 1. Route-Based Lazy Loading

React.lazy() allows a component to be loaded only when it is needed. This reduces the amount of JavaScript that is sent during the first page load. Instead of importing all route-specific components immediately, the browser fetches them only when visiting that route.

In this project, the route-based pages were updated to use dynamic imports for the heavy sections that are not required on the initial app load.

### 2. Suspense Fallback

React.Suspense handles the loading state while a lazy-loaded component is being fetched. A fallback spinner or message is shown so the user understands that the page is still loading. This is especially useful when a route is loaded over a slower network connection.

The app uses a lightweight loading spinner with a clear message such as “Loading page…” to keep the UI consistent and easy to understand.

### 3. Additional Heavy Component

The selected heavy component was the GitHub repositories page (`GithubRepos`). It is suitable for lazy loading because it fetches data from the GitHub API, renders a list of repositories, and includes search/filter functionality. Loading this page only when the user navigates to `/repos` keeps the initial landing page lighter and avoids fetching unnecessary code and data immediately.

### 4. Code Splitting

Vite automatically creates separate JavaScript chunks when lazy-loaded components are used. These chunks are downloaded only when the user reaches the relevant route. This improves the initial loading experience by reducing the amount of code included in the main bundle.

## Key Questions

1. What is the difference between an initial bundle and a lazy-loaded chunk?
   An initial bundle is the main JavaScript sent when the app first loads. A lazy-loaded chunk is an extra code split that is downloaded only when the user visits a route or conditionally renders a component.

2. Why can lazy loading improve perceived performance even if the total amount of code eventually downloaded remains similar?
   Because users receive the essential code first, and non-critical features load later. This makes the app feel faster and more responsive during the first interaction.

3. When is lazy loading not worth the added complexity?
   Lazy loading is less valuable when a component is very small, used on nearly every page, or when the app is already light enough that the added code-splitting logic does not meaningfully improve performance.

## Errors / Troubleshooting

The project initially failed to run `npm run build` in PowerShell because script execution was blocked by the local execution policy. This was resolved by running the command in a PowerShell session with `-ExecutionPolicy Bypass`.

No application-level implementation errors were encountered after the lazy-loading update.

## Conclusion

Route-based code splitting improves initial loading performance by moving non-essential JavaScript into separate chunks. The browser loads the main bundle first and fetches the additional chunks only when the user navigates to features such as Projects, Contact, or the GitHub repositories page. This approach reduces the time to interactive experience and makes the app feel faster without sacrificing functionality.
